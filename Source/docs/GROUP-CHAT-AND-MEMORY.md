# v0.25 — party identity, group conversations and memory

This release separates three identities: a game actor, a named Convai character definition, and a save-memory timeline. A spawn request’s random ID becomes the party member ID. `characterId` stays the roster key, such as `anca`; `label` adds a visible copy number. Anca #1 and #2 therefore have independent transforms, AI ownership, tactics and dismissal, but reuse the same Convai profile ID, session ID and end-user scope. There is one active `ConvaiClient`, not a cloud character or connection allocated for every spawn. Switching characters disconnects the prior room after saving its session and reconnects the next profile with its cached session. Reconnecting to another Anca resumes Anca’s existing conversation.

## Party implementation

`companions.lua` now keys `members` by spawn request instead of definition. Its protocol retains the existing MEMBER columns and adds IDENTITY rows containing the definition key, display label, actor path, distance and availability. Node validates that spawn commands reference the roster while other commands reference a current member instance. The helper separates SUMMON and YOUR PARTY lists. It rebuilds list items only when identities change, preserves selection, and updates individual text/badge values without moving focus or recapturing the cursor.

The Companion tab and its Follow/Hold/Attack buttons are removed. Tactics is the first page, followed by Orders and Help. Automatic behavior defaults to follow, frontline, aggressive, player-target preference and no health/stamina withdrawal. If no selected hostile target is eligible, native enemy queries provide another target. Advanced saved graphs still support their original movement vocabulary; the normal menu never sends Hold. The pursuit slider is gone. Internal combat sensing stays bounded at 20 m around the player; a follower farther than 24 m temporarily withdraws and must rejoin within 9 m before engaging again. This hysteresis avoids oscillating between retreat and attack at one threshold. Native unbreakable actions finish before the adapter reclaims following.

The configured party limit is zero, meaning no gameplay cap. Native v6 uses a growing ownership registry rather than eight fixed entries. Allocation is checked for integer/size overflow and failure; failure leaves existing owners intact. Entries store paths and root ownership, not long-lived unvalidated UObject pointers. A new DLL filename permits loading v6 alongside the currently loaded v5. Old cleanup closures retain v5 until its population owners are stopped; their tables must not be overwritten with v6 methods before cleanup. This distinction matters because each DLL owns its own registry.

Arrival slots retain the first three fan directions, then spread subsequent reservations around expanding rings. Each request makes at most 24 navigation projections, verifies player clearance, vertical separation and clearance from live/pending members, then recalculates just before spawning. A request fails with an open-ground instruction if no position qualifies. The registry can grow; native construction, navigation space and game resources are still real constraints. The existing async class/CDO loader and staged loading UI remain in use. These changes do not promise hitch-free actor construction.

## Group orchestration

Convai is used for one character response at a time. `group-chat.mjs` supplies the missing multi-character orchestration locally. F8/F9 selects a group room ID in Lua. Aimed selection uses the existing 4.5 m body-friendly direction score; group fallback finds a visible humanoid within 12 m. Additional candidates come from the owned party snapshot, not a full-world scan each frame. Unavailable, fighting, distant or duplicate-definition candidates are excluded.

The addressed character is always first. At most two other distinct definitions are chosen using `companion-lore.json`. Confirmed family/friend ties receive more weight than general faction associations. Explicit names and matching topics can override a weak association; distance breaks close choices. Unmapped ties remain unknown. These weights are selection policy, not factual measurements of friendship. Anca–Leonica, Pieter–Vladimir, Bakr-Erga–Ocha and Crake–Drogos have specific documented connections; the court is a faction association, not an invented circle of best friends. The [coverage file](../characters/QUEST-KNOWLEDGE.md) links the sources for every companion.

Each round has a unique room, token, speaker index and generation. Text submission sends the original Coen message to the first speaker. Dynamic context contains labeled utterances heard so far; later NPC replies are not submitted as if Coen said them. A voice turn uses the SDK’s final user transcription and marks the first request already sent, preventing a duplicate answer to the original spoken message. Capture is disabled after that group utterance and remains off during replies.

`ReplyTracker` excludes messages predating the request, tracks current final text, and waits for speaking/thinking and the blendshape queue to finish. It adds a short quiet interval, and allows extra time for TTS to begin after LLM text. It never declares completion merely because the connection started idle. The bridge then writes a fixed GROUP mailbox command. Lua validates the room, prior generation and owned member ID, releases the previous facial/AI hold, reacquires the next actor and publishes a fresh generation. Only then can the client send the next request and facial frames. Old tokens and frame generations are rejected. Failed selection skips that speaker; a missing response times out after 90 seconds. New selection, loss of game heartbeat or leaving the conversation cancels the round. No arbitrary code is accepted through the mailbox.

The F6/F7/F8 callbacks left in the stable UE bootstrap are no-ops in normal conversation mode. The Windows helper owns F6/F7/F8/F9 and uses the existing balanced game-input lease. Selection acknowledgement also waits for the matching overlay room, avoiding a race where the composer could bind to the prior target’s generation. Subtitles show the current speaker and a GROUP label when relevant. Audio still plays through WebView2/AudioRenderer, with the existing Lua MetaHuman facial mapping; no new native lip-sync driver was introduced.

## Knowledge, hearing and cloud memory

The original system supplied nine curated grants (Anca four, Lacra four, Marat one). It sampled the journal every ten seconds, read only the selected ending, matched exact recipients and copied approved sentences into dynamic context and SDK memory. It did not upload the full journal. This release retains that design and expands it to 32 rules covering all 17 summonable identities. The biographies, relationship types, topics and source links live in `companion-lore.json`; the quest conditions and approved facts live in `quest-knowledge.json`.

Static biography describes a character’s own identity, not future game progress. Quest grants require exact title, captured ID prefix and `EQS_Success`, plus an ending regex where a fact depends on a branch. Shared events are separated from later optional disclosures. Completing Ocha’s personal quest does not tell her mother its outcome: the separate return/report quest must finish. Vladimir remembers his discussion with Coen but not the subsequent report to Crina. Xanthe’s remote excavation discoveries are withheld even when those quests complete. Catalin’s outpost memory requires completed Rise at Dawn; its active state in the observed save grants nothing. A summoned boss can remember an encounter without pretending that summoning rewrote the story outcome. See [the detailed policy and sources](../characters/QUEST-KNOWLEDGE.md).

Group hearing is a separate evidence class. At each completed utterance, the local scheduler records its ID, attributed speaker and nearby eligible listeners. `HeardMemory` stores up to 100 recent events per named character and timeline, offers the latest 12 in context, and deduplicates events across polling and clones. Text is explicitly labeled as a reported statement, not verified history or an instruction. Only those listeners receive the record; other characters’ private quest context is never copied into the room. The SDK’s own session history continues to retain private conversations. These safeguards limit what the mod provides; they cannot guarantee a language model never invents or repeats a claim.

The journal ledger contains hashes plus progress-stage metadata solely for local rollback detection. An active quest becoming successful/failed is ordinary progress and now retains the timeline. Missing quests, regressed states, changed completed endings or a policy change create another timeline/end-user scope. Earlier cloud memories remain in their previous scope rather than being deleted globally. Initial migration from old opaque hash records is conservative. Save files are not transactionally integrated with the cloud, and switching saves with indistinguishable journal progress cannot be detected reliably. Context refreshes use `updateContext({mode:'replace',run_llm:'false'})`, and memory writes use `memoryManager.addMemories()` with acknowledgement/retry bookkeeping. Surroundings remain fresh temporary region/time/precipitation context.

## Provisioning and validation

`provision-companion-extras.py` reads the existing API key locally, lists owned managed characters, creates only missing named definitions, checkpoints creation immediately, selects catalogue voices, configures `fast-gemma-4-31b-it`, and reads voice/backstory/model back before marking success. Bakr-Erga is stored as “Bakr Erga” in the Core API because its name validator rejects the hyphen; in-game naming and aliases retain it. Ten additional profiles were verified. Catalogue voices express approximate tone and are not cloned game-actor voices. The model is the configured latency-oriented option, not a measured fastest-model claim. Normal launching and clone spawning never run provisioning.

Offline checks cover protocol authentication, clone command identity, guarded AI lifetime, frame generations, group handoff, first voice-turn deduplication, public-hearing scope, quest branches, rollback progression and real browser-client behavior against an SDK mock. The client test verifies one request per speaker, no handoff during speech and reuse of a named session by another clone. The native test grows through 40 mock owners and exercises cleanup/reuse; assertions are explicitly enabled even under Zig’s optimized C build. All Lua sources parse, TypeScript checks, C# builds, and UI fixtures were rendered at reference and smaller sizes. No game input, live group conversation or physical microphone testing was performed. [TEST-NEXT](../TEST-NEXT.md) gives the user check.

The earlier [porting methodology](../README.md) documents the UE4SS reflection dumps, proven facial controls, native combat handoff and crash investigation. This extension uses those established engine interfaces; it does not infer native callable actions from wiki text. When porting, discover and validate the other game’s identity, journal, facial and AI contracts before reusing this orchestration layer.
