# Companion implementation and porting notes — v0.25

Current combat/lifecycle behaviour is documented in [the v0.26.7 review](COMPANION-REVIEW-V0267.md); conversation/memory architecture is in [the group and memory notes](GROUP-CHAT-AND-MEMORY.md). The sections below preserve history. Tactical graphs, party caps, pursuit controls and earlier hotkeys are superseded; campaign AI owns fighting.

## v0.24.6: arrival reservations, initial facing and clear defaults

The overlap was a two-stage async placement bug. `spawn` originally computed a count-dependent angle, but `pollLoading` discarded it when refreshing the destination and sent every factory call to `player yaw + 90`, 240 cm away. Both stages used the player's own yaw for the companion's orientation. Correcting only the initial request could never fix the eventual spawn transform.

Each party member now reserves the lowest free summon slot before streaming. The pure `companion_recovery.summonPoint` function receives the current player location/yaw, this slot, a bounded list of occupied positions and the navigation projector. The first three slots prefer a fan at 0/+75/−75 degrees. A bounded search checks eight angles on each of three radii (300/420/540 cm). It evaluates the **projected** result, requiring at least 200 cm from the player, 240 cm of horizontal separation from other live/pending companions, no more than 650 cm from the player and no more than 250 cm vertical difference. If navigation collapses several candidates onto one narrow island, they remain rejected. This is navigation and party-spacing validation, not a claim of a full collision sweep against every world object; native spawning still determines the final actor transform.

The selection runs for the initial reservation and again immediately before the native spawn factory, using live positions for attached members and reserved positions for loading/spawning members. The refreshed point is stored before requesting native spawn, so another pending summon can avoid it. A failed search reports that the player should use open ground; it does not silently stack actors. There is no per-frame placement scan or global actor enumeration. Dismissal frees a slot while retaining the other members' actual occupancy, so count reuse cannot recreate the old overlap bug.

Yaw is `degrees(atan(player.Y − spawn.Y, player.X − spawn.X))`, measured from the projected point. After the pawn attaches, one guarded `K2_SetActorRotation` corrects facing from its actual position toward the player's latest position. It preserves pitch/roll and skips dead, suspended, combat, cinematic or unbreakable-action states. `arrivalFaced` prevents repetition on normal ticks or streaming reattachment. The existing native follower/combat systems own all later turns; this does not add a conversation hold or freeze idle animations. Slot, requested position and yaw are appended to the loading trace for the user's gameplay check.

New members and the unsummoned UI settings both default to Follow, Frontline, Aggressive, Player target, 20 m pursuit, 25% health recovery and 15% stamina recovery. Aggressive selects eligible nearby hostiles without requiring an already-engaged enemy. It still uses the existing hostility/target/range checks and does not change the character's attack rate, cooldowns or repertoire. User-applied tactics remain member-owned and are not overwritten by a background default reset.

The fourth F5 tab is Help. Four topic buttons (Getting started, Tactics, Orders, Troubleshooting) update four fixed title/body blocks. All controls use the existing reference-canvas scaling, nonactivating input lease and change-only text updates. Help works without a spawned member, has no game commands and leaves Enter/Ctrl+Enter bound only to Orders. The UI preview fixture renders all four topics plus a reduced-size Help view. Two focused Lua tests cover multiple reservations, slot reuse, player movement, projected-point collisions and bounded failure; the complete companion test set now has 18 passing cases. Final engine placement and visible orientation remain for the user's short two-companion check.

The complete repertoire is not a static list of currently granted GAS classes. Do not fix an apparently empty list by granting guessed abilities or calling them at arbitrary intervals. Also do not delete a player-target guard without inspecting the dependent behavior: a boss move can rely on player-specific targeting, encounter state or animation interactions.

The manager now only establishes native combat equipment, state, allegiance and target ownership, then yields movement/action selection to the combat tree. `TryActivateAbilityByClass`, manual power dispatch and the eight-second automatic-power loop are removed. Read-only grant snapshots remain at the existing bounded cadence for diagnosis; an inspection failure only logs an error and cannot change combat or show a capability restriction. The C# menu removes its power picker, activation button, grant-status explanation and automatic-power card. The generated Lua/JSON roster contains character definitions only. The order compiler, JSON graph validator and Lua wire validator reject `power` nodes; legacy saved plans containing them are skipped on load, preserving the original file until the next explicit save. The authenticated command endpoint rejects a stale manual power request rather than queueing it. Tactical settings need only six values. The seventh configure wire field and MEMBER columns 12/17 stay reserved (empty/zero) so separate helper/Lua reloads cannot shift health, stamina or detail fields. Legacy `POWERINFO` rows and power columns are ignored by the bridge and are no longer emitted or shown.

Validation covers both legacy text/JSON/wire command rejection and preservation of tactics and saved valid plans, alongside the existing combat/catch-up cases. The change does not require a new native DLL or a game restart. The user observes native special-move selection during ordinary play; successful attacks and catch-up are already confirmed.

Ability grants are reread after setup and periodically thereafter. This is a targeted repair hypothesis based on missing setup, not proof of successful attacks or a claim that humanoid Lacra now has her wolf-form powers. Native activation still decides grants, target requirements, cost, cooldown, movement and damage.

Lifetime handling now distinguishes detachment from dismissal. Full native culling can require returning to the area before the population supplies its pawn again.

It projects a point 250 cm behind Coen onto navigation, adds the follower's scaled capsule half-height, then uses collision-checked `K2_TeleportTo`. ## v0.24.2: combat rejection and crash investigation

The 12 September 15:11:28 crash was an access violation reading `0x294` on the game thread, in UE 5.5.4 / `dw1-pc-256914-shipping-patch2-all`. Evidence is preserved in `runtime/crash-v0241/`. `scripts/analyze-companion-crash.py` reads the **exception stream's** register context (the ordinary thread context was captured later by the crash reporter), maps executable RVAs through the PE unwind table, and disassembles the fault using local `pefile`, `capstone` and `minidump` packages. This is offline analysis, with no executable patching or raw-address calls added to the mod.

The exception instruction at RVA `0x5cddcd2` reads `[rax+0x294]`, with exception `RAX=0`. Its preceding instruction loads `[AIStub+0x1a8]`. The captured UE4SS reflection dump identifies these offsets as `RebelAIStub.AIBoard` and `RebelAIBoard.Weapon`. The enclosing native thunk starts at `0x5cddbf8`, exactly matching the dump's `BP_IsWeaponEquipped` native pointer after accounting for the prior session's image base. The call stack passes through UE4SS's Lua-to-UFunction bridge. It identifies the unsafe function, but does not distinguish the three former Lua call sites (travel stance, combat stance, diagnostics).

All three calls are removed. `ai_state.board` checks validity/destruction flags, reacquires the current board, verifies it is the expected owned board, checks `IsInitializedAndHasPawn`, and verifies board identity again. `weaponEquipped` reads `Weapon.TagName` only after those checks and returns nil for an unavailable board, distinct from false for a stowed weapon. Companion ticks, stance restoration, target eligibility, conversation diagnostics and cleanup use these checks. A valid UObject alone does not establish that its pawn and board are still attached. Lua `pcall` cannot contain a native access violation.

The log separately showed five `combat entry: false` results. Ambrus's final snapshot was `combat=false`, `bCanFight=true`, following disabled, and actual `Target=Coen` with Friendly attitude. Offline inspection of the native `StartCombatBehaviors` implementation (RVA `0x5d06eb8`) revealed an early return when `bCanFight && !bIsDead` is already true; another guard rejects an existing `Combat.bInCombat`. The old adapter set `bCanFight=true` immediately before calling this enable function, guaranteeing rejection for a living idle clone. `ai_state.startCombat` now checks the live clone and enemy, excludes scenes and unbreakable actions, lowers **only the owned clone's** gate immediately around that call, and restores its previous value if the call declines or raises a Lua error. A successful call enables combat itself. This sequence is specific to the inspected build and must be rechecked for another game/version.

The companion adapter now calls `SetCombatInstigator` once per prepared enemy, alongside the forced-target lease and owned pair attitudes. Its inspected native implementation requires a non-null instigator and accesses both boards while registering combat/perception relationships; it is never called with nil. It uses `bKeep=true` for an NPC instigator, so the clone's relation is reapplied as a temporary owned relation and restored at encounter cleanup. This API registers the enemy; it does not justify claiming the actual target changed until gameplay diagnostics confirm it. `SetForcedTarget(nil,0)` is used only to clear our owned lease on a live board; its native implementation explicitly handles a null target. No quest actor is recruited or reconfigured by the F5 party controller.

The policy retains a combat-start budget across target changes and brief perception gaps. It makes at most three attempts, ten seconds apart; ten seconds with no eligible target re-arms that budget for a later encounter. A rejected start clears owned hints and immediately restores the requested follow mode, without stopping a fight that never began. An accepted start is not replayed on target changes or a slow intro. Lost targets receive a three-second grace period. Passive/recovery or retreat exits defer follow control until an unbreakable native action finishes. Role positioning is issued only for active combat, not rejected entry. Diagnostics include the entry reason and actual/forced target.

Weapon restoration uses the reflected `EquipWeapon(bPlayAnim=false)` on combat handoff. Starting an equip montage immediately before checking for an unbreakable action could otherwise block entry and repeat the equip/stow cycle. Travel stowing retains its animation. A busy action before entry gets a 750-ms readiness retry without consuming a combat-start attempt.

Validation: all 17 Lua files parse, and no former native weapon-helper call remains. The 13 companion runtime/order/protocol checks pass, including new regressions for target churn after rejection, immediate follow restoration, unbreakable retreat, detached/replaced/destroying boards, and the native enable gate with rejection/error rollback. The focused conversation hold/restore test also passes, including detached-board inspection. The six changed Lua files are copied to the enabled game installation and their hashes match the workspace. These simulations establish adapter invariants; they do not demonstrate a boss landing attacks or exclude other engine crashes. ## v0.24.1 follow responsiveness

The user reported slow departure and walking at long distance after the neutral idle change. A read-only capture confirmed `CurrentCharacterState=Neutral`, `FollowerSpeed=0` (Walk), and a combat-defense movement profile with a 425 cm/s maximum. The native follower runner and walker assets were also inspected without loading or changing them: maximum speeds 450 and 140 cm/s, priority 0; the defense profile has priority 1. These are profile settings, not measured moving speeds. Changing a maximum speed alone would not select a running animation or resolve a profile conflict, so shared movement profiles remain untouched.

`companion_combat.followPace` now computes a distance/speed policy with separate run entry and exit thresholds. Frontline/flank spacing is 180 cm, movement threshold 245 cm, run entry 400 cm, run exit 265 cm. A player moving at least 280 cm/s also requests Run once outside the move threshold. Rearguard uses a 350 cm spacing and ranged uses 450 cm, with the same threshold margins. Planar distance avoids treating a nearby player directly above/below as a long catch-up path.

`companions.followMovement` checks this policy every 250 game milliseconds using only the two known actors' positions and player velocity. Heavy enemy discovery, plan execution and combat decisions keep their old cadence. The follower board's thresholds are written when the role/spacing changes; its Walk/Run enum is requested only on a pace transition. The pose adapter likewise switches between the character's advertised Neutral and Running states on transitions, retaining the original state for combat restoration. It does not repeatedly reapply the state, replay the follow action, manipulate global profile priorities, or force movement during a battle/scene. Hold, conversation and combat release only a speed value still owned by the mod. Combat can replace either travel state normally.

One new focused policy test covers a stationary distant player, jogging departure, ordinary walking, settling nearby, boundary oscillation and role spacing. The six runtime tests pass. UE4SS hot reload verifies module loading; physical movement remains a user gameplay check. `companion-follow-before.txt` preserves the pre-change live capture, and recurring per-companion diagnostics now include native velocity, profile, speed enum, path availability, gap and catch-up request.

## v0.24 loading feedback and travel stance

Ambrus's previous summon was requested at 14:32:14 and attached at 14:32:25. Character and AI load requests, factory creation and activation measured below the millisecond timer's resolution; those timings do not cover the engine's later loading/actor construction. The prior code inspected `NPCDefinition.PawnClass` but did not preload it. The new sequence is definition → Pawn class → AI definition → reaction class → population spawn → validated party attachment. All four class requests use the existing native v5 async loader. Only explicit Summon triggers loading; browsing the roster does not preload every boss.

`StaticFindObject` can find a class before loading has finished. `companion_native.loadedClass` now checks the class and its CDO for NeedInitialization, NeedLoad, NeedPostLoad, NeedPostLoadSubobjects, BeginDestroyed and FinishDestroyed flags. It avoids touching the CDO while the class has these flags. This uses the documented [UE4SS UObject flag API](https://docs.ue4ss.com/dev/lua-api/classes/uobject.html) and [EObjectFlags table](https://docs.ue4ss.com/lua-api/table-definitions/eobjectflags.html). This is a completion gate, not a claim that every soft reference in an AI graph or skeletal mesh is loaded. No blocking loader or worker-thread UObject access was introduced. See [Epic's async loading guidance](https://dev.epicgames.com/documentation/en-us/unreal-engine/asynchronous-asset-loading-in-unreal-engine).

Lua emits up to eight `SUMMON` records in each complete party snapshot: request ID, companion ID, phase and message. A command ACK only means the request was accepted. `ready` is published after the owned pawn resolves in the current world, its initialized AI stub and board are valid, friendship/follower setup succeeds, and the initial stance/power inspection finishes. Load failure or dismissal changes that request's record to `failed`. Phase timestamps plus native request/factory/activation timings go to `runtime/companion-loading-<id>.txt`.

The native Windows helper owns `CompanionLoading`, a small state machine bound to the request ID, member ID, party epoch and current menu session. A 40 ms UI timer animates only the small bar surface, independent of UE's game-thread updates. Stage labels describe progress; the UI never fabricates a percentage. During a pending summon it tolerates a stale game heartbeat for at most 120 wall-clock seconds while Dawnwalker stays foreground. The bridge's timestamp is checked locally too, so an unchanged JSON file cannot pretend the game is updating. Close keys remain active. Failure leaves the menu open with its reason; reload/world change cancels the pending close. Ready requires the matching record, an attached member and fresh game state, then displays briefly before releasing the input lease and hiding F5. Manually closing disarms this completion handler, so a later menu session cannot be closed by the old request. The background summon continues.

A read-only capture of the existing Ambrus, taken before reload cleanup, showed `Follower / Idle`, no combat, no equipped weapon, and `CurrentCharacterState=None`. His actual `AIDef_Ambrus` exposed Default, Running, several Combat states and Neutral. Therefore the fix operates on the native character-state interface instead of forcing an animation Boolean. `travelPose` checks the clone's advertised states and `BP_CharacterStateExist`, then calls `BP_SetCharacterState` with the supported Neutral tag when the old state is None, Default or Combat. It snapshots a restorable state; None falls back to the advertised Default. If an equipped weapon exists, native `StowWeapon(true)` is requested once. Cinematics, suspended AI and unbreakable actions are excluded.

On combat entry the adapter restores only a Neutral state that it still owns; a state already changed by native AI is preserved. It re-equips only a weapon it successfully stowed. Restoration defers while an unbreakable action runs. Native combat still chooses attacks, movement and animation; the mod does not disable animation ticking, teleport bones or continually force the neutral state. Unsupported characters retain native behavior. The visual outcome of Neutral on each boss remains a gameplay check, not something the reflected tag name proves.

Validation: the helper builds; 14 C# assertions cover readiness, ACK-only responses, wrong request/character, missing pawn, old menu sessions, epoch changes, failure, pause messaging and stale-state limits. Eight Node/Fengari checks cover the existing companion contract plus class/CDO readiness. Offscreen 720p and 1080-reference renders include the loading state. They are UI fixtures, not game captures. Reproduce the loading lifecycle test after building `ConvaiHost.next.exe` with `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/Test-CompanionLoading.ps1`. ## Roster and player controls

F5 opens the roster in the same native Windows helper that hosts the conversation UI. There is no added Electron process. The form uses the existing Afacad font and dark/gold palette, scales to the game client rectangle, keeps the game in foreground and captures real keys only while open. F5 or Esc closes it. Opening F5 releases the current conversation before accepting party orders, so two controllers do not compete for the same NPC. Movement/look ignore flags and cursor visibility are leased through the existing UI mailbox and restored on close or heartbeat loss.

There are **three active slots** and these **17 candidates**: Anca, Lacra, Bakir, Ambrus, Xanthe, Brencis, Crake/Marat, Uriash Matriarch/Bakr-Erga, Leonica, Ocha, Vicho, Drogos, Sara, Catalin, Pieter, Vladimir and Isbrand. The supplied “Ambrose” maps to Ambrus, and the Sara asset is spelled Sarah. Bakir, Ambrus and Xanthe use the installed CoenHelper-named definitions first. Those names are evidence of intended assistance in some game context, not proof that the variants work everywhere.

The menu offers spawn, dismiss, dismiss all, follow/regroup, hold, attack the player's native target, and:

| Setting | Implemented request | Limit |
| --- | --- | --- |
| Defensive / aggressive / passive | Assist engaged enemies / select eligible nearby hostiles / withhold the clone's combat gate | This is engagement policy, not a native attack-frequency multiplier. |
| Frontline / rearguard / left or right flank / ranged preference | Project a role-dependent point onto navigation and submit `BP_SetPreferredLocation`; adjust follower distances | RebelAI can choose another movement/action. Ranged preference does not prohibit melee. |
| Player target / protect / nearest / weakest | Rank eligible enemies from the native subsystem | Protection prioritizes enemies whose target is Coen; it does not intercept every projectile. |
| Pursuit 5–30 m | Filter targets around the player, or the held-position anchor | Native combat navigation; the separate 24 m off-camera catch-up applies only outside combat while following. |
| Low health / low stamina | Stop requested combat and regroup, then resume after a higher recovery threshold | No free healing. Set a threshold to zero to disable it. Missing/unexpected fractions do not trigger the rule. |
| Character abilities (no menu setting) | The character's native combat/action trees choose when to use them | Native target, form and encounter conditions apply; player-specific boss moves may not run against NPCs. |

Native AI config classes are shared CDOs. Changing their ticket cooldowns or aggression traits could change every NPC using the same configuration. This build does not edit those shared settings. Strict attack-type restrictions, automatic clones/summons, transformations and encounter teleports remain outside the enabled controls. Summon ownership, faction propagation and boss phase requirements need separate work before exposing them as general commands.

## How the assets were found

The local UE4SS object dump supplies reflected classes, functions, property kinds, sizes and names. A read-only `AssetRegistryHelpers.GetAssetRegistry()` query then used `GetAssetsByPath` on known NPC/enemy/quest roots and filtered `NPCDef_`, `AIDef_`, `AIConfig_` and `GA_AI_`. It found 2,698 distinct matching assets, including 113 AI ability definitions. The result is `runtime/companion-asset-catalog.tsv`; `docs/companion-native-evidence.tsv` contains the selected API evidence.

An RC5 detail mattered: returned **struct** array entries from this query needed `assets[i]:get()` before reading `AssetName`, `PackageName` and `PackagePath`. Reading the wrapper directly produced missing values. UObject array returns and live struct arrays must be handled according to their actual wrapper type; do not apply `:get()` indiscriminately. See the loader author's [Dawnwalker UE4SS notes](https://www.nexusmods.com/thebloodofdawnwalker/mods/18) and [UE4SS SDK generator documentation](https://docs.ue4ss.com/dev/feature-overview/sdk-generator.html).

Lore names came from the [publisher character directory](https://en.bandainamcoent.eu/dawnwalker/the-blood-of-dawnwalker/characters) and the [character glossary](https://www.gamerguides.com/the-blood-of-dawnwalker/database/glossary/characters). Local package names supplied the actual runtime candidates. Lore was not used as proof of a native ability, combat trait or compatible pawn. The broader [research survey](COMPANION-POSSIBILITIES.md) distinguishes reflected hooks, mod policy and experimental ideas.

`scripts/Build-CompanionResearch.mjs` indexes the raw evidence. `scripts/Build-CompanionConfig.mjs` converts the selected character definitions into matching Lua/JSON config files. It contains no manual ability allowlist; native action trees define each character's repertoire. Generation fails if a required character override is absent from the captured catalogue.

## Why a small native bridge was necessary

The facial adapter is still Lua. Population spawning introduced a separate problem: this game's reflected soft-class parameters occupy **40 bytes**, while the RC5 Lua soft-reference wrapper copies a different layout. Earlier Lua soft-reference conversions failed; an engine access violation cannot be recovered by Lua `pcall`. Suppressing the Lua error or retrying the same conversion would not fix the ABI.

`bridge/native-source/companion_native.c` is a narrow C DLL compiled with portable Zig 0.14.1. The live file is `bridge/native/companion_native_v3.dll`. It uses UE4SS's exported reflection functions to resolve named objects, functions and properties, inspect offsets/parameter sizes, initialize/copy/destroy engine property values, and call `ProcessEvent` on the game thread. It checks the expected 40-byte soft class, 32-byte path and 24-byte FVector layouts. It does not pin addresses from a previous process or construct a second Lua runtime.

The exported Lua-callable function deliberately takes no Lua arguments and returns no Lua values. The Lua wrapper writes a bounded, fixed-operation request file, calls the C entry point, then checks the matching ID in its reply. That avoids sharing strings or userdata through a separately linked Lua ABI. The native operation set is fixed: `probe`, `loadclass`, `inspect`, `spawn`, `poll`, `stop`, `stopall`. Returned text is parsed as data, never executed. This remains native code and cannot contain an engine crash; a future game/loader build requires renewed ABI validation.

Class loading uses the game's own `MakeSoftClassPath → Conv_SoftClassPathToSoftClassRef → LoadClassAsset_Blocking` functions. `inspect` exports only the known pawn, AI-definition and reaction class fields from the NPC definition CDO. Anca resolved to `BP_NonPlayerCharacter`, `AIDef_Anca` and `AIReactions_Human_QuestCombatant`. This load/inspect chain succeeded in the paused game. See [UE4SS UClass documentation](https://docs.ue4ss.com/dev/lua-api/classes/uclass.html) for CDO access and [Epic's soft-object pointer API](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/CoreUObject/FSoftObjectPtr) for the distinction between references and resolved objects; the local build's measured sizes govern this adapter.

## Spawn ownership and lifecycle

On an explicit spawn command, Lua finds a nearby point on navigation, loads the chosen NPC and AI classes, and asks `SpawnPopulationActorAsyncAction.RunAsyncAction` for a population spawner. The native bridge builds game-sized soft-class buffers using `Conv_ClassToSoftClassReference`, roots the returned async action and activates it. There are eight native ownership slots as an additional bound; the UI/Lua party limit is three.

Lua polls only that action's `Spawner.SpawnedPawns` export. It resolves pawn paths contained in that export and checks class/world validity. It does not scan for an arbitrary nearby character and call that a successful spawn. A definition yielding multiple pawns is rejected. Spawning times out after 20 **unpaused game seconds**, retaining diagnostics and requesting owned-spawner cleanup.

After resolving an initialized pawn/stub, the manager establishes pairwise friendship with Coen and existing party members, enables the native temporary follower fields, disables return-to-community-action-point behavior and resets the clone's initial goal once. It retains the pairwise attitude values for cleanup. No global faction table or shared definition is modified. An AI definition allows requesting the clone's combat gate, but does not prove the pawn has useful combat actions.

Dismissal cancels the graph, releases holds, restores pairwise attitudes, requests despawn on the owned stub and stops the owned population spawner. The C DLL refuses to stop actions outside its ownership table. Only after the stop request succeeds does it clear the root/slot. Confirm actual disappearance in gameplay: an accepted request is not observation of a completed despawn.

World changes, time resets and hot reload clear the party; saved order graphs remain. Lua does not serialize UObject handles into a save or recreate party members automatically. The native ownership table survives Lua reload, so cleanup must run before a new manager takes over. The RC5 external `require` cache retains module tables even when `package.loaded` is cleared; the update explicitly migrates the earlier native probe table and extends the running loader's shared watch list. Ordinary companion Lua edits now use the existing stable router without another game launch.

## Combat, powers and scheduling

The manager uses `RebelAISubsystem.GetEnemyStubsInRange` around Coen instead of scanning all actors each frame. Queries and member decisions are limited to about once per 750 ms, with bounded candidate processing. It rejects player, dead, untargetable, cinematic, non-hostile and out-of-radius targets. A short `SetForcedTarget` request and `StartCombatBehaviors` let native AI execute. A foreign forced target is preserved. No continuous transform or attack-montage forcing is used.

Health/stamina are accepted only as finite 0–1 fractions from the known combat component. Recovery has hysteresis: exit requires health at least 0.15 above its entry threshold and stamina at least 0.30 above its threshold. Rules do not synthesize healing or stamina. Conversation or native-scene ownership pauses plan timing and companion control; the conversation's existing idle-preserving hold handles facing. Party membership survives F7 and normal conversation release.

Ability diagnostics read granted `GameplayAbilitySpecContainer.Items[].Ability` references at a bounded cadence and write only when the class list changes. They are not a complete list of attacks: standalone native fragments can supply abilities on demand. The mod has no power activation loop or button. Native combat/action trees decide which ability to use under their own ticket, target, form, cost and cooldown conditions. Some boss branches explicitly require a player target; this adapter does not rewrite that condition for NPC combat. The v0.24.5 section above records the captured evidence and its limits.

## Orders and transport

The companion panel does not need an LLM round trip for each order. `compileOrder` implements a deliberately small English grammar, for example:

```text
protect me then flank left then attack my target
be aggressive then frontline then attack my target
when your health is below 30 percent, regroup then hold position
```

Unknown instructions are rejected. “Your health” means the addressed companion; ambiguous “my health” is rejected rather than silently checking the wrong actor. “Ranged only” is rejected; `prefer ranged` is supported. Enter previews the compiled steps, Ctrl+Enter or Run submits them. Named plans are saved locally and can be reused. Free-form LLM tactical planning and Convai-to-party graph generation are not implemented; the existing conversation action system remains separate.

The canonical JSON graph has version, ID, start, transition budget and up to 24 nodes. Each node has `id`, `op`, `value`, `timeoutMs`, `success`, `failure`. Explicit JSON graphs can be submitted to the authenticated `/companions` endpoint with `op: "plan"` and `graph`. JSON callers may use explicit branches; the menu's English compiler builds a sequence with failure edges to `failed`. Both JS and Lua validate operations, values, IDs, references, reachability, exits and a maximum 96 transitions. Closed loops without a terminal path are rejected, and even valid loops have a budget. No input becomes Lua or JavaScript code.

The Lua runner enters at most one node per tick. Conditions wait up to their timeout, rather than evaluating as an immediate `if`. Follow, role and stance nodes complete when intent is accepted, not when navigation arrives. Attack completes when native combat accepts the request, not when the enemy dies. Use `when the target is clear` for a later gate. Failures take the declared failure edge; cancellation stops future steps and leaves the last persistent intent in place. Game pause freezes timers. Commands waiting in the transport expire after 60 wall-clock seconds and must be reissued after a long pause.

The Node queue is serialized and bounded to eight commands. It tags each command with a random ID, party epoch and timestamp; Lua rejects stale epochs/replays/expired data. Party state is TSV with a matching `END` epoch marker so a partial write is not accepted. Node publishes an atomic JSON view for the form. The local HTTP host validates Host/Origin and a random session token. Config/presets are data, not executable scripts. This is the same service/process boundary used by the Convai transport, with a separate party epoch so a new conversation does not invalidate companions.

## v0.23 — asynchronous loading, combat handoff and AI ability ownership

The user reported several seconds of stalling during summon, unavailable/missing powers, and a companion standing still while repeating an attack line. The log confirms Ambrus spawned as `BP_Ambrus_Clone_C` at 13:59:43 and became unavailable about 64 seconds later; Lacra spawned at 14:01:24 and became unavailable about 87 seconds later. The precise cause of those unloads was not traced. Both the temporary clone choice and insufficient spawner lifetime ownership were reviewed.

The previous combat adapter re-enabled `Follower.bFollowerModeEnabled` every update, called `StartCombatBehaviors` every 2.5 seconds, supplied a forced target lasting only two seconds, and overwrote preferred positions every 1.5 seconds. Thus the target could lapse before refresh and combat entry could repeatedly interrupt its own introduction while follow/positioning competed for movement. `companion_combat.lua` now owns the transition policy: disable following on entry, request native combat once, renew an eight-second target lease every three seconds without restarting combat, and give perception gaps three seconds before exiting. A declined start has at most three attempts, ten seconds apart. An accepted but slow introduction is never treated as a reason to restart. Recovery/passive transitions stop once, clear the mod's target/position hints, and restore following. Native forced targets from another system remain respected.

Role positioning now gives a single, brief opening preference for each target/role change and releases it after three seconds or when an unbreakable action begins. Frontline uses native combat movement without a preferred-location tether. This is a tactical approach preference, not strict formation enforcement throughout every attack. Do not continuously force coordinates or restart combat to implement a role.

Pairwise friendship with Coen did not change the former villain's relationship to an enemy from the same faction. The adapter now temporarily marks the chosen Coen-hostile enemy and owned companion as mutually hostile. The dump verifies Hostile=3, Friendly=1. Only selected enemies already hostile to Coen are eligible; global faction definitions are not changed. These per-encounter overrides are bounded and restored on combat exit or dismissal, provided the game has not replaced the value itself.

The power lookup now uses the reflected `RebelAIStub.GetAbilitySystemComponent()` instead of assuming the Pawn's component lookup is the AI's ASC. Granted specs are read directly, and derived ability classes can match a mapped base ability. The complete observed grant list is saved when it changes. UI state distinguishes loading, no AI ASC, read error, unmapped native actions, and a power not currently granted. More candidates were added from the captured catalogue: Lacra's right wolf strike, Leonica's AoE, and Isbrand's scream. Regular Bakir, Ambrus and Xanthe definitions replace the summoned helper/clone definitions. This does not grant abilities or bypass their native requirements. Some NPCs have no mapped manual special; that is not evidence that their native weapon/action combat is absent. [Epic's Gameplay Ability guidance](https://dev.epicgames.com/documentation/unreal-engine/using-gameplay-abilities-in-unreal-engine) explains the distinction between owning/granting an ability and successfully activating it.

The summon path no longer calls `LoadClassAsset_Blocking`. Native v5 uses `KismetSystemLibrary.LoadAssetClass` through reflected game-sized parameters: 40-byte soft class, 16-byte delegate and 24-byte latent info. It validates Linkage/UUID/ExecutionFunction/CallbackTarget offsets, leaves the delegate unbound and uses INDEX_NONE linkage, then lets Lua poll the known class path. No Unreal API is called from an arbitrary background thread. Lua reserves a party slot, waits for the character class, inspects its AI reference, waits for that class, reprojects near the player's current position and only then invokes population spawning. Each stage is bounded by unpaused game time. A cancelled pending summon can finish caching an asset but does not create a pawn. See [Epic's asynchronous asset loading documentation](https://dev.epicgames.com/documentation/unreal-engine/asynchronous-asset-loading-in-unreal-engine) and [latent action info](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/FLatentActionInfo).

The actual population spawner is now rooted while owned, independently of the short-lived async action. The adapter records whether it added that root and removes only its own root during cleanup. It still resolves recorded paths before operations. A pre-existing root is preserved. Missing-player/world transitions dismiss the owned party so an old spawner is not retained indefinitely through a menu/load transition. The old v3/v4 DLLs remain mapped but new requests use `companion_native_v5.dll`; no live DLL was overwritten or unsafely unloaded.

Unreal still creates actors and initializes components on the game thread. Async asset loading cannot promise zero spawn hitch. The native bridge now records `factoryMs` and `activateMs`, and Lua saves per-character loading timings. It also writes AI behavior/phase, movement mode, target/attitude, follower state, unbreakable-action status, ASC and grant count every five unpaused seconds for owned companions. No global object scan is performed by these diagnostics.

Validation: seven focused Node/Fengari checks pass, including a 45-second simulated encounter with exactly one combat-start call, perception-gap recovery, target lease refreshes, slow-intro preservation and bounded rejected-entry retries. The standalone native lifecycle test covers cleanup/root ownership and world unload. Native and Windows helper builds pass. The paused game acknowledged one `LoadAssetClass` request for Anca in less than the millisecond timer's resolution; this was not an unloaded-asset or spawn benchmark. No agent-driven fight was performed. The user's next single-companion combat test remains necessary.
